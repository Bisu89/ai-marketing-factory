# 13 — AI Story (Claude-generated Spanish marketing narration scripts)

**Commit:** pending (see `git log` for the actual hash once committed).

## What it does

Turns a Library video's metadata -- title, topic, emotion, tags, notes, all
editable since Epic 12 -- into a ready-to-use **Spanish-language marketing
narration script**, generated by Claude. The user picks a video and one of 6
fixed storytelling styles (Cảm động / Hài hước / Truyền cảm hứng / Kịch tính /
Giáo dục / Bán hàng), clicks "Tạo Story", and gets back 2 distinct script
variants (title + narration text, 30-90s spoken length) to choose between.
This is the first feature in the app calling an external paid API, and
`app/modules/README.md` had explicitly anticipated a `story` module by name
since early in this project's history.

## Why synchronous, not a background job

Scene Cutter and Video Composer both run a queue + worker thread because
ffmpeg/edge-tts work takes tens of seconds to minutes. An LLM text-generation
call is fast (single-digit seconds), so Story generation is a **plain
synchronous request/response** -- no job queue, no `_recover_pending_jobs()`,
no polling `useEffect` on the frontend. This is a deliberate departure from
the pattern established by the other two modules, not an oversight -- a
future reader looking for the queue/worker in this module won't find one on
purpose. The result is still persisted (2 tables, `StoryJob` + `StoryVersion`)
purely for history/audit, written once inside the same request.

## Architecture

`app/modules/story/` -- a self-contained vertical slice per the
`app/modules/README.md` convention (own tables, own schemas/service/router,
never imported by another module or by core).

- `models.py` -- `StoryJob` (video_id FK, style, status `completed`/`failed`,
  error_message, created_at) + `StoryVersion` (story_job_id FK, version_index,
  title, script_text, is_selected).
- `schemas.py` -- `StoryGenerateIn`, `StoryJobOut`/`StoryVersionOut`.
- `service.py` -- `StoryService.generate()` loads the video via the core
  `Video` model directly (title/`category_name`/`emotion_name`/tags/notes),
  builds a Spanish-language system prompt encoding the chosen style and the
  30-90s/no-fabrication constraints, and calls
  `client.messages.create(model="claude-sonnet-5", output_config={"format":
  {"type": "json_schema", ...}}, ...)` -- **one API call, not two** -- asking
  for exactly 2 variants in a single structured-output response
  (`{"variants": [{"title", "script_text"}, {...}]}`). On any failure
  (missing key, network, refusal, malformed output) a `StoryJob(status=
  "failed", error_message=...)` row is still written for history, and the
  router raises the new `ExternalServiceError` (502) instead of a raw 500.
- `router.py` -- `POST/GET /story-jobs`, `GET /story-jobs/{id}`,
  `POST /story-jobs/{id}/versions/{id}/select`, `DELETE /story-jobs/{id}`.

## Model choice: Claude Sonnet 5, 2 variants in one call

Chosen over Opus 5 (unnecessary cost for a short script) and Haiku 4.5 (risks
not meeting the epic's explicit "chất lượng"/quality bar) as the best
quality/cost balance for creative marketing copywriting. Requesting both
variants via a single structured-output call (rather than 2 separate calls)
is cheaper, faster, and lets both variants share the same context -- the
JSON schema constrains the *shape* of the output but (per Anthropic's
structured-outputs support) can't constrain an exact array length, so the
system prompt asks for exactly 2 and the service validates `len(variants) >=
2` after parsing, truncating to 2 if the model returns more.

## Anthropic API key (Settings)

The first feature needing a network credential. Followed the existing
`update_library_dir()` pattern in `app/core/config.py` exactly:
`anthropic_api_key: str | None` on `Settings`, `update_anthropic_api_key()`
writing `APP_ANTHROPIC_API_KEY` via `dotenv.set_key()` +
`get_settings.cache_clear()`, and a new `PUT /settings/anthropic-key`
endpoint. `GET /settings` only ever returns `has_anthropic_key: bool` --
**never** the key value itself. `SettingsPage.tsx` gained a password-style
input + save button for it.

## Frontend

New dedicated Sidebar page (`/story`, `StoryPage.tsx`) rather than embedded in
the Library detail drawer -- the user's explicit choice. Video picker mirrors
Scene Cutter's Library-search-and-select pattern (`fetchVideos` debounced
search); supports a `?video_id=` URL param for future deep-linking from the
Library drawer, consistent with this app's URL-search-params-driven UI
convention. The "Tạo Story" button is disabled with an inline link to
Settings when `has_anthropic_key` is false. Results render as 2 side-by-side
version cards with a "Chọn phiên bản này" button (`is_selected`); a history
list below shows past generations for the selected video.

## Verification

Real end-to-end tests against the actual running backend (not mocked):

- Imported a real test video via `POST /videos`, confirmed `GET /settings`
  reports `has_anthropic_key: false` initially.
- `POST /story-jobs` with no key configured returns a clean `400` ("Chưa cấu
  hình Anthropic API key...") with no `StoryJob` row written.
- Invalid `style` returns `422` (Pydantic validation); non-existent
  `video_id` returns `404` -- neither creates a stray job.
- `PUT /settings/anthropic-key` persists correctly and flips
  `has_anthropic_key` to `true`; confirmed a subsequent `POST /story-jobs`
  actually reaches Anthropic's servers (got a real `401 authentication_error`
  back from the API for the deliberately-fake test key, not a client-side
  validation error) -- confirms the request shape (model id,
  `output_config.format`, message construction) is accepted up to the auth
  check. The failed attempt correctly persisted a `StoryJob(status="failed",
  error_message=...)` row with 0 versions, and `DELETE /story-jobs/{id}`
  removed it cleanly.
- Frontend: `tsc -b` type-checks clean; Vite's dev server transforms
  `StoryPage.tsx`, `SettingsPage.tsx`, and `App.tsx` without error (200, no
  compile errors). A live interactive browser click-through (Playwright) was
  **not** performed in this session -- no browser-automation tool was
  available -- so the actual generate-with-a-real-key flow and the rendered
  UI have not been visually confirmed. The user opted to test the real
  generation flow themselves via the UI once they add their own key.
- Test video and the temporary fake API key used for wiring verification were
  both cleaned up afterward; `story_job`/`story_version` tables confirmed
  empty and `has_anthropic_key` back to `false` before handing off.
